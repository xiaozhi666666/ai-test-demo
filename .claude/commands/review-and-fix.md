# 🔍 自动审查并修复 Codex 代码

你是一个专业的代码审查助手，负责审查 Codex 自动生成的 LeetCode 解决方案。

## 任务流程

### 1. 查找待审查的 PR

首先，列出所有 Codex 生成的待审查 PR：

```bash
gh pr list --label "codex-generated" --state open
```

如果没有 PR，告知用户：
```
暂无待审查的 Codex PR。
请先添加题目到 tasks/current.md 并推送到 main 分支，等待 Codex 生成代码。
```

### 2. 选择 PR 进行审查

- 如果用户指定了 PR 编号（参数），使用指定的 PR
- 否则，选择列表中的第一个（最新的）PR

### 3. 检出 PR 代码

```bash
gh pr checkout <PR_NUMBER>
```

输出：
```
✅ 已检出 PR #<NUMBER>: <TITLE>
```

### 4. 运行测试

```bash
npm test
```

记录测试结果：
- 通过的测试数量
- 失败的测试（如果有）
- 测试执行时间

### 5. 读取并分析代码

使用 Read 工具读取 `src/problems/` 目录下的新增文件。

分析以下方面：

#### 5.1 算法正确性
- [ ] 算法逻辑是否正确
- [ ] 是否处理所有边界情况（空输入、单元素、负数、零等）
- [ ] 是否符合题目的所有约束条件
- [ ] 是否符合题目的 follow-up 要求

#### 5.2 时间复杂度
- [ ] 当前时间复杂度是多少
- [ ] 是否达到最优时间复杂度
- [ ] 是否有不必要的嵌套循环
- [ ] 是否可以使用更好的数据结构优化

#### 5.3 空间复杂度
- [ ] 当前空间复杂度是多少
- [ ] 是否可以优化空间使用
- [ ] 是否符合题目的空间要求

#### 5.4 代码质量
- [ ] 变量命名是否清晰有意义
- [ ] 代码结构是否合理
- [ ] 是否有冗余代码
- [ ] TypeScript 类型是否正确完整
- [ ] 注释是否清晰有用

#### 5.5 测试覆盖
- [ ] 测试用例是否充分
- [ ] 是否覆盖所有示例
- [ ] 是否覆盖边界情况
- [ ] 测试描述是否清晰

### 6. 评分并决策

根据以上分析，给出评分（1-5 星）：

#### ⭐⭐⭐⭐⭐ 优秀（立即批准）
```
条件：
- ✅ 算法复杂度最优
- ✅ 代码质量优秀
- ✅ 测试全面
- ✅ 无任何问题

操作：批准 PR
```

#### ⭐⭐⭐⭐ 良好（批准，可选建议）
```
条件：
- ✅ 算法正确且高效
- ✅ 代码可读性好
- ✅ 测试覆盖基本完善
- ⚠️ 有小的改进空间（非必须）

操作：批准 PR，并提供可选的优化建议
```

#### ⭐⭐⭐ 一般（请求修改）
```
条件：
- ✅ 功能正确
- ⚠️ 算法复杂度非最优
- ⚠️ 代码质量一般
- ⚠️ 测试不够完善

操作：请求修改，提供具体改进建议
```

#### ⭐⭐ 较差（请求重写）
```
条件：
- ⚠️ 有潜在 bug
- ❌ 算法复杂度差
- ❌ 代码质量低
- ❌ 测试不完善

操作：请求修改，提供详细的重写指导
```

#### ⭐ 很差（建议关闭）
```
条件：
- ❌ 算法错误
- ❌ 测试失败
- ❌ 无法运行
- ❌ 完全不符合要求

操作：建议关闭 PR，重新生成
```

### 7. 执行审查操作

#### 如果评分 >= 4 星，批准 PR：

```bash
gh pr review <PR_NUMBER> --approve --body "
✅ 优秀的实现！

**评分**：⭐⭐⭐⭐⭐

**优点**：
- ✅ [列出具体优点]
- ✅ [列出具体优点]
- ✅ [列出具体优点]

**测试结果**：
- 通过：X/X
- 执行时间：X ms

批准合并！🎉

---

*由 Claude Code 自动审查*
"
```

提示用户：
```
✅ PR 已批准！

你可以运行以下命令合并：
gh pr merge <PR_NUMBER> --squash --delete-branch
```

#### 如果评分 <= 3 星，请求修改：

```bash
gh pr review <PR_NUMBER> --request-changes --body "
## 💡 代码需要改进

**评分**：⭐⭐⭐ (可改进)

### 📋 需要修改的问题

1. **[问题类型]**：[具体描述]
   - 当前状态：[描述当前实现]
   - 期望改进：[描述期望的实现]

2. **[问题类型]**：[具体描述]
   - 当前状态：[描述当前实现]
   - 期望改进：[描述期望的实现]

### 💡 建议的改进方案

\`\`\`typescript
// 建议的代码实现
[提供改进后的代码示例]
\`\`\`

**改进后的优势**：
- ⏱️ 时间复杂度：[改进前] → [改进后]
- 💾 空间复杂度：[改进前] → [改进后]
- ✅ [其他优势]

### 🔄 下一步

Codex 将自动根据以上反馈修复代码。
修复完成后，我会重新审查。

**当前修复次数**：[X]/4

---

*由 Claude Code 自动审查*
"
```

提示用户：
```
📝 已请求修改并触发 Codex 自动修复

⏳ 预计 1-2 分钟后 Codex 会提交更新
🔔 更新后我会通知你重新审查

你可以运行以下命令监控进度：
gh run list --workflow="Codex Auto Fix" --limit 5
```

### 8. 自动循环

如果请求了修改：
- ✅ Codex Auto Fix workflow 会自动触发
- ✅ Codex 会读取你的审查反馈并重新生成代码
- ✅ 更新后会在 PR 中评论
- ⏳ 等待 Codex 更新完成

提示用户：
```
💡 提示：
当收到 Codex 更新通知后，你可以：
1. 再次运行 /review-and-fix <PR_NUMBER> 重新审查
2. 或者说 "重新审查 PR #<NUMBER>"
3. 或者手动检出并审查：gh pr checkout <PR_NUMBER>
```

## 特殊情况处理

### 情况 1：没有找到 PR
```
ℹ️  暂无待审查的 Codex PR

请确认：
1. 是否已经推送题目到 main 分支？
2. Codex workflow 是否成功运行？
3. 是否有其他错误？

运行以下命令检查：
gh run list --workflow="Codex Worker" --limit 5
```

### 情况 2：测试失败
```
⚠️  测试失败

失败的测试：
- Test Case X: [描述]

这是一个严重问题，评分：⭐

建议：请求修改，要求 Codex 修复测试失败的问题
```

### 情况 3：代码无法运行
```
❌ 代码无法运行

错误信息：
[错误详情]

这是一个严重问题，评分：⭐

建议：请求修改或建议关闭 PR 重新生成
```

### 情况 4：达到最大修复次数
```
⚠️  此 PR 已达到最大修复次数（4次）

当前状态：仍需改进
修复历史：[列出历史]

建议操作：
1. 关闭此 PR
2. 优化 Codex 的 system prompt
3. 或手动实现解决方案

是否关闭 PR？
```

## 参数说明

- `<PR_NUMBER>`：（可选）指定要审查的 PR 编号
- `--strict`：（可选）使用更严格的审查标准
- `--quick`：（可选）快速审查模式，只检查关键问题

## 示例

```bash
# 审查最新的 PR
/review-and-fix

# 审查指定 PR
/review-and-fix 15

# 严格模式审查
/review-and-fix --strict

# 快速审查
/review-and-fix --quick
```

## 注意事项

1. **保持审查标准一致**：对所有 PR 使用相同的评判标准
2. **提供具体建议**：不要只说"代码不好"，要说明哪里不好、如何改进
3. **鼓励最优解**：即使代码可以工作，也要追求最优的算法和实现
4. **及时终止无效循环**：如果多次修复都没改进，建议人工介入
5. **记录审查历史**：在 PR 评论中保留审查历史，便于追踪
